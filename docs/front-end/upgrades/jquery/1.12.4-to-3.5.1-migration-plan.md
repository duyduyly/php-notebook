# jQuery 1.12.4 → 3.5.1 Migration Plan

> **Purpose:** Upgrade a legacy application from jQuery `1.12.4` to `3.5.1` using controlled compatibility checkpoints, with security validation, rollback gates, and regression testing at every stage.
>
> **Important:** The official jQuery guidance does **not** require deploying every intermediate 3.x minor release. Because `1.12.4` is already newer than jQuery `1.9`, it can be migrated to jQuery 3.x with **jQuery Migrate 3.x**. This document intentionally uses incremental checkpoints to reduce risk in legacy applications with old templates, plugins, modules, or custom JavaScript.

## Overview

### Goal

Move from:

```text
jQuery 1.12.4
    ↓
jQuery 2.2.4
    ↓
jQuery 3.0.0
    ↓
jQuery 3.1.1
    ↓
jQuery 3.2.1
    ↓
jQuery 3.3.1
    ↓
jQuery 3.4.1
    ↓
jQuery 3.5.0
    ↓
jQuery 3.5.1
```

The patch releases above are used where available because they include fixes over the corresponding `.0` release:

| Requested checkpoint | Validation version |
|---|---:|
| `2.x` | `2.2.4` |
| `3.0` | `3.0.0` |
| `3.1` | `3.1.1` |
| `3.2` | `3.2.1` |
| `3.3` | `3.3.1` |
| `3.4` | `3.4.1` |
| `3.5` | `3.5.0` |
| Final target | `3.5.1` |

### Why use checkpoints?

For a legacy application, the main risk is usually not jQuery itself. It is application code or third-party JavaScript that depends on old jQuery behavior.

Typical risk areas include:

- removed or deprecated APIs;
- event behavior changes;
- Deferred/Promise behavior changes;
- HTML parsing and DOM manipulation changes;
- Ajax callback changes;
- old third-party plugins;
- CMS templates/modules/components bundling their own jQuery copies;
- multiple jQuery versions being loaded on the same page.

### Key principle

> **Do not continue to the next checkpoint until the current checkpoint passes compatibility, console, functional, and regression tests.**

## Target Upgrade Path

| Step | From | To | Main purpose | Risk |
|---:|---:|---:|---|---|
| 0 | — | `1.12.4` | Establish reproducible baseline | Low |
| 1 | `1.12.4` | `2.2.4` | Remove legacy IE 6/7/8 dependency and validate 2.x behavior | Medium |
| 2 | `2.2.4` | `3.0.0` | Major compatibility boundary | **High** |
| 3 | `3.0.0` | `3.1.1` | Stabilize 3.0 behavior and Deferred/ready changes | Low–Medium |
| 4 | `3.1.1` | `3.2.1` | Validate dimensions/events and new deprecations | Low–Medium |
| 5 | `3.2.1` | `3.3.1` | Validate plugin compatibility and deprecations | Low |
| 6 | `3.3.1` | `3.4.1` | Apply prototype-pollution security fix | Medium |
| 7 | `3.4.1` | `3.5.0` | Apply DOM/XSS security fixes and HTML parsing changes | **High** |
| 8 | `3.5.0` | `3.5.1` | Apply 3.5.0 regression fix | Low |

> The most important gates are **2.x → 3.0** and **3.4.x → 3.5.x**.

## Security Coverage

The migration is intended to remove the following known vulnerabilities associated with old jQuery versions.

| CVE | Main issue | `1.12.4` | Fixed by checkpoint |
|---|---|---|---:|
| CVE-2015-9251 | Cross-domain Ajax / XSS-related behavior | Affected | `3.0.0+` |
| CVE-2019-11358 | Prototype Pollution in deep `jQuery.extend()` | Affected | `3.4.0+` |
| CVE-2020-11022 | XSS in DOM manipulation / HTML handling | Affected | `3.5.0+` |
| CVE-2020-11023 | XSS in DOM manipulation / HTML handling | Affected | `3.5.0+` |

### Security state during migration

```text
1.12.4 / 2.2.4
├── CVE-2015-9251  ❌
├── CVE-2019-11358 ❌
├── CVE-2020-11022 ❌
└── CVE-2020-11023 ❌

3.0.x → 3.3.x
├── CVE-2015-9251  ✅
├── CVE-2019-11358 ❌
├── CVE-2020-11022 ❌
└── CVE-2020-11023 ❌

3.4.x
├── CVE-2015-9251  ✅
├── CVE-2019-11358 ✅
├── CVE-2020-11022 ❌
└── CVE-2020-11023 ❌

3.5.0 / 3.5.1
├── CVE-2015-9251  ✅
├── CVE-2019-11358 ✅
├── CVE-2020-11022 ✅
└── CVE-2020-11023 ✅
```

> **Security note:** Reaching `3.5.1` addresses these four CVEs by version, but it does not prove the entire application is secure. Application-level XSS, unsafe HTML insertion, vulnerable third-party plugins, and duplicate old jQuery bundles still need to be checked.

## Migration Rules

Apply these rules at every checkpoint.

1. **Never upgrade production first.** Use a development/staging environment.
2. **Upgrade one jQuery checkpoint at a time.** Do not mix unrelated JavaScript refactors into the same change.
3. **Record the exact jQuery version** before and after every checkpoint.
4. **Keep jQuery Migrate temporary.** Use it to identify compatibility problems, fix them, then remove it.
5. **Do not load jQuery Migrate 1.x and 3.x together.**
6. **Do not manually overwrite CMS/vendor files if the framework provides an asset manager or package update mechanism.**
7. **Audit for duplicate jQuery bundles** from templates, modules, plugins, themes, or third-party components.
8. **Keep rollback available at every checkpoint.**
9. **Do not accept a checkpoint with unexplained browser-console errors.**
10. **Functional parity is required before proceeding.**

### Confirm the loaded version

Browser console:

```javascript
jQuery.fn.jquery
```

Expected example:

```text
"1.12.4"
```

Search repository bundles:

```bash
grep -RIn "jQuery v" . \
  --include="jquery*.js" \
  --exclude-dir=node_modules \
  --exclude-dir=.git
```

Also inspect the browser Network/Sources panels because an extension may load a jQuery copy that is not obvious from the primary application bundle.

## Step 0 — Baseline jQuery 1.12.4

### Objective

Create a stable baseline before changing any dependency.

### Actions

- [ ] Confirm the application actually loads jQuery `1.12.4`.
- [ ] List every jQuery file in the repository.
- [ ] Identify which package/template/module/plugin owns each jQuery file.
- [ ] Detect duplicate jQuery loads on representative pages.
- [ ] Capture browser-console errors before migration.
- [ ] Capture current jQuery Migrate warnings, if Migrate is already loaded.
- [ ] Run the regression test matrix.
- [ ] Record screenshots or automated visual baselines for critical pages.
- [ ] Create a Git tag/commit or equivalent rollback point.

### Inventory example

| Asset | Owner | Version | Loaded? | Action |
|---|---|---:|---|---|
| `/js/jquery.min.js` | Application | `1.12.4` | Yes | Upgrade |
| `/plugin-x/jquery.js` | Plugin X | Unknown | Conditional | Investigate |
| CDN jQuery | Template | Unknown | Yes | Remove duplicate |

### Exit gate

Proceed only when the current application behavior is reproducible and the test baseline is documented.

## Step 1 — Upgrade 1.12.4 → 2.2.4

### Objective

Validate that the application does not depend on jQuery 1.x browser compatibility behavior, especially IE 6/7/8 support.

### Why `2.2.4`?

`2.2.4` is the final jQuery 2.x release. jQuery 1.12.x and 2.2.x had largely aligned APIs, but jQuery 2.x removed old IE compatibility code.

### Actions

- [ ] Replace the active `1.12.4` asset with `2.2.4` in development/staging.
- [ ] Confirm `jQuery.fn.jquery === "2.2.4"`.
- [ ] Test browser support requirements.
- [ ] Test selectors, events, DOM manipulation, Ajax, animations, forms, and third-party plugins.
- [ ] Review console errors.
- [ ] Run the full regression matrix.

### jQuery Migrate

For this checkpoint, Migrate `1.x` can be useful when legacy behavior predating jQuery 1.9 still exists indirectly through old plugins.

Do **not** carry Migrate 1.x into the jQuery 3.x checkpoint.

### Exit gate

```text
Functional regression tests: PASS
Console exceptions:          0 unexplained
Critical UI flows:           PASS
Rollback tested:             YES
```

## Step 2 — Upgrade 2.2.4 → 3.0.0

### Objective

Cross the most important major-version compatibility boundary.

### Risk level

**High.** jQuery 3.0 intentionally removed deprecated APIs and changed some behaviors.

### Required tool

Load the uncompressed development build of **jQuery Migrate 3.x** after jQuery while testing.

Example pattern:

```html
<script src="jquery-3.0.0.js"></script>
<script src="jquery-migrate-3.x.js"></script>
```

Use the development/uncompressed Migrate build so warnings are visible in the browser console.

### High-priority compatibility checks

- [ ] `.size()` usage.
- [ ] `.andSelf()` usage.
- [ ] old event aliases such as `.load()`, `.unload()`, `.error()` used as event shortcuts.
- [ ] `jqXHR.success()`, `jqXHR.error()`, and `jqXHR.complete()`.
- [ ] Deferred/Promise behavior.
- [ ] `.ready()` behavior and errors thrown inside ready handlers.
- [ ] event ordering or `.trigger()` assumptions.
- [ ] custom selectors/plugins using undocumented jQuery internals.
- [ ] third-party UI widgets.

### Example replacements

```javascript
// Old
$(".item").size();

// New
$(".item").length;
```

```javascript
// Old
$(".child").andSelf();

// New
$(".child").addBack();
```

```javascript
// Old
$.ajax(url).success(onSuccess).error(onError);

// New
$.ajax(url).done(onSuccess).fail(onError);
```

### Exit gate

- [ ] All critical pages load.
- [ ] All critical interactions work.
- [ ] All actionable JQMIGRATE warnings are fixed or explicitly documented.
- [ ] No dependency requires jQuery `< 3.0` without an approved remediation plan.
- [ ] Regression matrix passes.

## Step 3 — Upgrade 3.0.0 → 3.1.1

### Objective

Stabilize the initial jQuery 3.x migration and verify Deferred/ready error behavior.

jQuery 3.1.0 changed how errors from ready handlers are surfaced; `3.1.1` subsequently delivered patch fixes without intended compatibility changes for applications already on jQuery 3.x.

### Actions

- [ ] Upgrade to `3.1.1`.
- [ ] Keep jQuery Migrate 3.x during validation.
- [ ] Test all document-ready initialization.
- [ ] Test Deferred/Promise chains.
- [ ] Check for previously hidden JavaScript errors now appearing in the console.
- [ ] Run regression matrix.

### Exit gate

No new errors or behavior regressions compared with the accepted 3.0 checkpoint.

---

## Step 4 — Upgrade 3.1.1 → 3.2.1

### Objective

Move through the 3.2 line using `3.2.1`, which contains hotfixes for regressions found shortly after `3.2.0`.

### Focus areas

- [ ] `.width()` / `.height()` behavior.
- [ ] inline elements and dimensions.
- [ ] checkbox/radio click triggering.
- [ ] deprecated APIs reported by Migrate.
- [ ] custom CSS-property usage.
- [ ] templates/components that calculate element dimensions for sliders, modals, menus, or carousels.

### Exit gate

Layout, dimensions, click behavior, and regression matrix must match the accepted baseline.

---

## Step 5 — Upgrade 3.2.1 → 3.3.1

### Objective

Validate third-party plugin compatibility and prepare the codebase for later security-sensitive releases.

### Actions

- [ ] Upgrade to `3.3.1`.
- [ ] Test plugins using class manipulation APIs.
- [ ] Re-run all Migrate checks.
- [ ] Re-run application-wide legacy API searches.
- [ ] Validate Ajax and Deferred workflows.
- [ ] Run regression matrix.

### Note

The `3.3.1` built runtime is effectively the recommended packaging follow-up to `3.3.0`; jQuery published it immediately after a release packaging/dependency issue.

### Exit gate

Zero unexplained JavaScript errors and no critical plugin regressions.

## Step 6 — Upgrade 3.3.1 → 3.4.1

### Objective

Apply the security fix for **CVE-2019-11358** and validate code that performs deep object merges.

### Security focus

Audit code such as:

```javascript
$.extend(true, target, source);
```

Pay particular attention when `source` can contain user-controlled or remotely supplied data.

### Actions

- [ ] Upgrade to `3.4.1`.
- [ ] Search for deep `$.extend(true, ...)` calls.
- [ ] Review whether merged objects contain untrusted data.
- [ ] Test focus/blur behavior.
- [ ] Test AMD/module-loading paths if applicable.
- [ ] Test iOS/browser-specific code where applicable.
- [ ] Run regression matrix.

### Security gate

At this checkpoint:

```text
CVE-2015-9251  ✅ addressed by version
CVE-2019-11358 ✅ addressed by version
CVE-2020-11022 ❌ not yet addressed
CVE-2020-11023 ❌ not yet addressed
```

## Step 7 — Upgrade 3.4.1 → 3.5.0

### Objective

Apply the jQuery 3.5.0 DOM-manipulation security changes that address **CVE-2020-11022** and **CVE-2020-11023**.

### Risk level

**High for legacy HTML-manipulation code.**

jQuery 3.5.0 changed `jQuery.htmlPrefilter` behavior for security reasons. Code that depends on old self-closing-tag normalization or unusual HTML strings may behave differently.

### High-priority audit

Search for code that inserts dynamic HTML:

```javascript
.html(...)
.append(...)
.prepend(...)
.before(...)
.after(...)
.replaceWith(...)
```

Focus especially on data originating from:

- URL/query parameters;
- API responses;
- database-generated HTML;
- CMS custom fields;
- user input;
- third-party widgets.

### Self-closing HTML patterns

Review non-void HTML elements written in self-closing style, for example:

```javascript
$("<div />");
```

Prefer properly closed HTML where needed:

```javascript
$("<div></div>");
```

### Actions

- [ ] Upgrade to `3.5.0`.
- [ ] Keep jQuery Migrate 3.x enabled for development diagnostics.
- [ ] Resolve HTML-related Migrate warnings.
- [ ] Test sliders, modal dialogs, dropdowns, select/options, dynamic lists, and Ajax-rendered HTML.
- [ ] Test forms that dynamically generate options or validation messages.
- [ ] Run XSS-focused tests on dynamic HTML entry points.
- [ ] Run complete regression matrix.

### Security gate

At this checkpoint all four CVEs in the scope of this plan are addressed by jQuery version.

---

## Step 8 — Upgrade 3.5.0 → 3.5.1

### Objective

Move to the final target and include the regression fix released after jQuery `3.5.0`.

jQuery `3.5.1` reverted an internal data-object change from `3.5.0` that had broken some plugins using `.hasOwnProperty()` against jQuery-managed data.

### Actions

- [ ] Upgrade to `3.5.1`.
- [ ] Re-test plugins that inspect jQuery `.data()` internals.
- [ ] Re-run all previous functional tests.
- [ ] Re-run security scanner.
- [ ] Confirm old jQuery files are not still publicly served or loaded.
- [ ] Resolve remaining Migrate warnings.
- [ ] Remove jQuery Migrate when all compatibility issues have been fixed.
- [ ] Test again **without jQuery Migrate**.

### Final runtime check

```javascript
jQuery.fn.jquery
```

Expected:

```text
"3.5.1"
```

## Legacy API Audit

### Repository searches

These searches are intentionally broad and may return false positives. Review each result manually.

```bash
# APIs removed or commonly problematic around the jQuery 3 migration
grep -RInE '\.(size|andSelf|live)\s*\(' . \
  --include='*.js' \
  --exclude-dir=node_modules \
  --exclude-dir=.git
```

```bash
# jqXHR callback methods removed in jQuery 3.0
grep -RInE '\.(success|error|complete)\s*\(' . \
  --include='*.js' \
  --exclude-dir=node_modules \
  --exclude-dir=.git
```

```bash
# Dynamic HTML insertion points — review for untrusted input
grep -RInE '\.(html|append|prepend|before|after|replaceWith)\s*\(' . \
  --include='*.js' \
  --exclude-dir=node_modules \
  --exclude-dir=.git
```

```bash
# Deep object merges — relevant to prototype-pollution review
grep -RInE '\$\.extend\s*\(\s*true' . \
  --include='*.js' \
  --exclude-dir=node_modules \
  --exclude-dir=.git
```

### Audit result table

| Finding | File | Owner | Risk | Fix | Status |
|---|---|---|---|---|---|
| `.size()` | — | — | Compatibility | `.length` | ⬜ |
| jqXHR `.success()` | — | — | Compatibility | `.done()` | ⬜ |
| Dynamic `.html()` | — | — | XSS | Validate/sanitize data flow | ⬜ |
| `$.extend(true, ...)` | — | — | Prototype Pollution | Validate source / upgrade | ⬜ |

## Rollback Strategy

Every checkpoint must be independently reversible.

### Before each upgrade

- [ ] Commit/tag current working state.
- [ ] Record current jQuery asset path and version.
- [ ] Preserve lockfile/package metadata where applicable.
- [ ] Record relevant CMS/extension asset configuration.
- [ ] Capture current test results.

### Rollback trigger

Rollback if any of the following occurs:

- critical page fails to load;
- checkout/login/form submission breaks;
- a required third-party plugin cannot run;
- unresolved JavaScript exceptions appear in production-critical flows;
- visual or behavioral regression has no safe fix in the checkpoint scope.

### Rollback procedure

```text
Failed checkpoint
      ↓
Restore previous dependency/version
      ↓
Clear application/CDN/browser asset cache
      ↓
Confirm jQuery.fn.jquery
      ↓
Run smoke tests
      ↓
Document failure and root cause
```

Do not continue to a later jQuery checkpoint hoping that an unexplained earlier regression will disappear.

## Definition of Done

The migration to `3.5.1` is complete only when all items below are true.

- [ ] Browser reports `jQuery.fn.jquery === "3.5.1"`.
- [ ] No page loads an older jQuery copy unintentionally.
- [ ] CVE-2015-9251 is no longer reported for the active jQuery runtime.
- [ ] CVE-2019-11358 is no longer reported for the active jQuery runtime.
- [ ] CVE-2020-11022 is no longer reported for the active jQuery runtime.
- [ ] CVE-2020-11023 is no longer reported for the active jQuery runtime.
- [ ] Critical user flows pass regression testing.
- [ ] No unexplained browser-console exceptions remain.
- [ ] jQuery Migrate warnings are resolved or formally accepted with rationale.
- [ ] Application passes tests after jQuery Migrate is removed.
- [ ] Third-party plugins/templates/modules are verified compatible.
- [ ] Rollback procedure has been documented.
- [ ] Final dependency/security scan has been captured as evidence.

## Maintenance Note

This plan intentionally stops at **jQuery 3.5.1** because that is the target of this migration scope.

jQuery `3.5.1` should not be interpreted as the current supported jQuery release. For a long-term modernization project, perform a separate compatibility/security assessment after this migration and consider moving to the currently supported jQuery branch.
