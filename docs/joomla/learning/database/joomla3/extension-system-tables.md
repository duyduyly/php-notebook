## 1. Extension Registration

Joomla stores installed components, modules, plugins, templates, libraries, packages, files, and languages in `#__extensions`.

The row describes the installed extension. The extension's business data may be stored in separate tables.

Example:

```text
#__extensions.element = com_content
```

identifies the Content component registration, not the article records themselves.

## 2. `#__extensions`

| Column | Meaning |
|---|---|
| `extension_id` | Extension primary key |
| `package_id` | Parent package extension ID |
| `name` | Extension name or language key |
| `type` | Extension type |
| `element` | Machine name, such as `com_content` or `mod_custom` |
| `folder` | Plugin group, such as `system` or `content` |
| `client_id` | Site or administrator client |
| `enabled` | Enabled state |
| `access` | Access level where applicable |
| `protected` | Core-protected extension flag |
| `manifest_cache` | JSON data read from the extension manifest |
| `params` | JSON extension configuration |
| `custom_data` | Extension-specific data |
| `system_data` | Internal system data in supported schemas |
| `checked_out` | User editing the record |
| `checked_out_time` | Checkout time |
| `ordering` | Plugin or extension ordering |
| `state` | Internal state where present |
| `namespace` | Namespace value in later Joomla 3 schemas where supported |

Common `type` values:

```text
component
module
plugin
template
library
package
file
language
```

For plugins, the unique identity is commonly based on:

```text
type = plugin
folder = system
element = cache
```

Extension IDs are installation-specific. Never assume `extension_id` is identical in Joomla 3 and Joomla 6.

## 3. Database Schema and Update Tables

### `#__schemas`

Tracks the installed database schema version for an extension.

| Column | Meaning |
|---|---|
| `extension_id` | Extension ID |
| `version_id` | Installed database schema version |

This table should match the extension update SQL state. Do not copy Joomla 3 core schema rows into Joomla 6.

### `#__update_sites`

Stores update source definitions.

Typical columns include:

| Column | Meaning |
|---|---|
| `update_site_id` | Update site ID |
| `name` | Display name |
| `type` | Update source type |
| `location` | Update XML/feed URL |
| `enabled` | Enabled flag |
| `last_check_timestamp` | Last update check |
| `extra_query` | Download key or query data where used |

### `#__update_sites_extensions`

Bridge table between extensions and update sites.

| Column | Meaning |
|---|---|
| `update_site_id` | Update site ID |
| `extension_id` | Extension ID |

### `#__updates`

Temporary cache of discovered updates.

Typical columns include update ID, update site ID, extension ID, name, description, element, type, folder, client ID, version, details URL, information URL, and extra query data.

This table is regenerated by update discovery and should not be migrated.

## 4. Redirect Tables

### `#__redirect_links`

Stores redirect records collected by the Redirect plugin or created by administrators.

| Column | Meaning |
|---|---|
| `id` | Redirect ID |
| `old_url` | Original URL |
| `new_url` | Target URL |
| `referer` | Referring URL |
| `comment` | Administrator note |
| `hits` | Number of requests |
| `published` | Enabled state |
| `created_date` | Creation timestamp |
| `modified_date` | Last modification timestamp |
| `header` | HTTP status code, where supported |

Migration should normalize domains and paths before importing redirects.

## 5. Messaging Tables

### `#__messages`

Stores private administrator messages.

Important columns commonly include:

```text
message_id
user_id_from
user_id_to
folder_id
date_time
state
priority
subject
message
```

User IDs must be remapped if messages are migrated.

### `#__messages_cfg`

Stores per-user messaging configuration.

Typical columns:

| Column | Meaning |
|---|---|
| `user_id` | User ID |
| `cfg_name` | Configuration key |
| `cfg_value` | Configuration value |

Administrator messages are often not required in a content migration.

## 6. Smart Search Tables

Joomla Smart Search uses the `#__finder_*` tables.

Main tables:

| Table | Purpose |
|---|---|
| `#__finder_links` | Indexed content records |
| `#__finder_terms` | Search terms and statistics |
| `#__finder_taxonomy` | Hierarchical taxonomy nodes |
| `#__finder_taxonomy_map` | Link-to-taxonomy mapping |
| `#__finder_links_terms*` | Link-to-term mapping partitions |
| `#__finder_tokens*` | Temporary indexing tokens |
| `#__finder_filters` | Saved frontend search filters |

Finder data is generated from source content. The safest approach is usually:

1. Migrate the real content.
2. Install and enable compatible Finder plugins.
3. Clear the target index.
4. Rebuild the index in Joomla 6.

Do not copy Joomla 3 Finder indexes directly into Joomla 6.

## 7. Other Supporting Tables

### `#__languages`

Stores configured content languages.

Important columns commonly include:

```text
lang_id
lang_code
title
title_native
sef
image
description
metakey
metadesc
sitename
published
access
ordering
```

### `#__content_types`

Defines content types used by tags, UCM, history, and routing integrations. IDs and JSON mappings may differ by Joomla version.

### `#__core_log_searches`

Stores legacy search terms and hit counts when search logging is enabled.

### `#__utf8_conversion`

Used by historical database conversion processes. It is not business data.

### `#__postinstall_messages`

Where present, stores post-installation notices and completion state. This is installation-specific system data.

### `#__overrider`

Where present, supports language override search/index behavior. Confirm the exact Joomla 3 minor-version schema.

## 8. Temporary and Runtime Data

The following data should normally be regenerated, cleared, or excluded:

```text
#__session
#__updates
#__finder_tokens*
#__finder_links_terms*
cache tables or extension caches
post-installation notices
temporary conversion tables
```

## 9. Migration Notes

- Install Joomla 6-compatible extensions before migrating extension-owned data.
- Map extensions by `type`, `element`, `folder`, and `client_id`, not by `extension_id` alone.
- Do not copy Joomla 3 core rows from `#__extensions` into Joomla 6.
- Do not copy `#__schemas`, update cache, or Finder index data.
- Preserve paid-extension download keys securely; do not commit them to Git.
- Review `manifest_cache`, `params`, and `custom_data` for obsolete options.
- Rebuild Smart Search after content migration.
- Normalize redirect domains and verify HTTP status codes.
- Confirm the exact source schema because Joomla 3 minor releases and extensions may add columns.
- Treat third-party extension tables as separate migration projects.
